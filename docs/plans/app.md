# App Implementation Plan

The developer-facing plan for building the frontend specified in `docs/plans/ui.md`,
consuming the serving contract from `docs/architecture/etl.md` stage 5 and
`docs/architecture/infrastructure.md`. Code-free, technical, parallel-safe: **frontend
development starts now, against fixtures, and flips to real pipeline output at ETL
milestone M2 with zero code changes.**

## 1. Toolchain

| Concern | Choice | Notes |
|---|---|---|
| Runtime / PM / tests | **Bun** | Same toolchain as the ETL; `bun test` for the data layer, workspace member of the repo root. |
| Framework | **React + TypeScript + Vite** | SPA, static build (`app/dist/`), served per infrastructure.md. Strict TS. |
| Routing / state | **react-router** + URL query params | The URL is the *only* filter/window state store (shareable links are a spec requirement). No global state library — server data is immutable per run; component state is local. |
| Query engine | **`@duckdb/duckdb-wasm`** | Loads manifest-selected Parquet partitions; all aggregation client-side. |
| Charts | **Recharts** (standard charts) + **custom SVG** (micro-viz) | Recharts: stacked bars, scatter, strip plot. Custom SVG components: sparklines, 3-segment micro-bars, tool-sequence strips, activity strips, heatmap — the honesty affordances (hatching, dotted small-n, ×N badges) need direct control. |
| Styling | **Tailwind** | Two side identities (ops steel-blue, product deep teal-green — see §6) as theme tokens; hatch patterns as shared SVG defs. |
| Lint / format | **Biome** | Same config as ETL. |

Dependency budget: `react`, `react-dom`, `react-router`, `@duckdb/duckdb-wasm`,
`recharts`, `zod` (via contracts) + dev tooling. Additions need written justification
here.

## 2. The parallelization keystone: `contracts/`

A new top-level workspace module, imported by **both** tracks:

- **Zod schemas for every published artifact**: `manifest.json` shape, and one row
  schema per table — `facts/turns`, `facts/tool_events`, `ref/sessions`,
  `ref/failure_signatures`, `ref/incidents`, `ref/capability_gaps`, `ref/gap_sessions`,
  `ref/findings`, `ref/auditor_timeline`, dims. Column names transcribed from
  `docs/architecture/derivations.md` / etl.md stage 5 — the schemas are the executable
  form of those docs.
- Shared enums and stable public keys (signature `pattern_id` format, outcome enum
  including `unclassified`/NULL semantics, provenance classes, `failure_verdict`).
- **ETL stage 5 validates its output against these schemas before publish; the app's
  query layer types every result row with them.** Contract drift between the tracks is
  a typecheck/test failure, not an integration surprise.
- Ownership rule: `contracts/` changes require touching the corresponding architecture
  doc in the same change; neither track edits it unilaterally to "make things fit."

**The fixture pack**: `contracts/fixtures/` contains a small generator script (runs on
Bun, uses DuckDB to write Parquet) that emits a synthetic `runs/<fixture-run-id>/`
tree — manifest + all partitions/reference files — populated from the contract schemas
with data shaped like the real dataset (skewed clients, a 76-turn session, an incident
window, undetermined/unclassified outcomes, a degraded-mode variant with NULL model
fields). Checked in (small); regenerated by script with reviewed diffs. This is what
`app` develops and tests against until ETL M2.

## 3. Module layout

```
app/
  src/
    main.tsx, router.tsx          routes per ui.md sitemap
    data/
      runtime.ts                  DuckDB-WASM lifecycle: init, register partitions, dispose
      loader.ts                   latest.json → manifest → window-selected partition fetch,
                                  immutable browser caching, loading/error surface
      queries.ts                  ALL SQL lives here, typed by contracts row schemas —
                                  one named query per UI construct
      window.ts                   time-window semantics: event-membership predicate,
                                  containment predicate + excluded-count query, URL codec
    state/
      urlState.ts                 filter bar + window ⇄ query params codec (the only store)
    components/
      shared/                     ProvenanceChip, StatedParam (⚙), CaptionBar,
                                  ExcludedSessionsCaption, GhostCard, DemoHatch defs,
                                  Sparkline, MicroBar3, ToolStrip (run-length), ActivityStrip,
                                  Heatmap
      ops/  product/  session/  findings/    one folder per route, components per construct
    pages/                        route components composing constructs + captions
  fixtures → contracts/fixtures/runs/…       (dev server serves this until M2)
```

Dependency direction: `pages → components → data → contracts`. `queries.ts` is the only
SQL location (mirrors the ETL's SQL-in-files convention); components never query —
they receive typed rows.

## 4. Data-layer design

- **Boot**: fetch `latest.json` → manifest (zod-validated against contracts — a
  malformed manifest is a rendered error state, not a crash) → read enrichment
  coverage → set degraded flags → fetch reference plane → register with DuckDB-WASM.
- **Window change**: compute needed fact partitions from manifest coverage, fetch only
  missing ones (browser cache + in-session registry), re-run the page's queries.
  Loading skeletons per partition fetch (infrastructure.md's "presents as REAL" rules).
- **Semantics enforcement lives in `window.ts`**, not scattered in SQL: the
  event-membership and containment predicates are composed into queries by helpers, so
  ops/product semantics cannot drift per-view. The excluded-count caption gets its
  number from the same helper that applies containment — one source of truth.
- **Degraded mode**: manifest coverage drives a `DegradedContext`; `M`-chipped
  constructs read it and render their degraded captions; `v_findings` rows are already
  filtered by `requires_enrichment` upstream.
- Failure posture: partition fetch failure → per-construct error state with retry;
  never a blank page; empty windows are first-class empty states.

## 5. Component conventions

- Every construct from ui.md is one component answering its named question; the
  question is the component's doc-comment and its rendered title.
- Honesty affordances are **shared components, not per-chart styling**: ProvenanceChip
  (H/C/M; unchipped = structural), StatedParam ⚙, CaptionBar ("N of M determined",
  "N excluded"), GhostCard, hatched-fill defs. A construct that needs a caption takes
  it as a prop from the query result — captions are data-driven, never hardcoded.
- Crossover links and all drill-downs are plain `<Link>`s built from `urlState.ts`
  codecs — every navigable state is a shareable URL by construction.
- No number formatting inline: one `fmt` module (counts, durations, percentages with
  explicit "~" for heuristic-derived values).

## 6. Appearance & visual design

The look is **financial-firm professional**: clean, dense-but-calm, modern, and
restrained. The data is the interface; decoration is absent. Rules and the technical
constructs that enforce them:

### Palette

- **Ink-first, near-monochrome base.** Backgrounds are white/near-white paper with a
  cool grey ink ramp (slate) for text, borders, axes, and structure. Charts sit on the
  page surface — no card-in-card nesting, no drop shadows beyond a 1px border and a
  subtle elevation on popovers.
- **No bright colors. No purple, anywhere.** Accents are desaturated and darkened:
  - **Ops identity: steel/slate blue.** **Product identity: deep teal-green.** The two
    rooms are distinguished by a restrained accent on the nav rail, page title
    underline, and active states — not by flooding surfaces with color.
  - Semantic failure red is a muted brick, used *only* for failure marks (red rings on
    tool blocks, failure series) — never for emphasis.
  - Provenance chips: `H` muted amber, `C` mid-slate, `M` **steel blue** (revised from
    the earlier violet — purple is banned). Chips are outline-style letters, not filled
    badges; identity is the letter + tooltip, color is secondary.
- **Chart color is computed, not eyeballed.** Categorical series (signature classes ≤7,
  4 clients, tool families) get one fixed-order theme drawn from desaturated financial
  hues (slate blue, teal, olive, amber, brick, warm grey), finalized at milestone A0 by
  running the dataviz palette validator (lightness band, chroma floor, CVD adjacent-pair
  separation, contrast) against our light surface — the passing hexes become Tailwind
  theme tokens. Hues are assigned to entities in fixed order and **never cycled or
  repainted when filters change the series count**.
- Sequential scales (the environments heatmap) are one hue light→dark (slate ramp);
  never a rainbow. Status/failure colors are reserved and never reused as series
  colors.

### Typography & density

- One typeface: **Inter** (self-hosted; no CDN), with **tabular numerals
  (`font-variant-numeric: tabular-nums`) mandatory in every table and metric** —
  columns of figures must align like a statement.
- Type scale is short: page title, section title, body, caption, mono-small (ids,
  matched snippets — monospace only for verbatim data/text, never for numbers).
- Tables are the app's core idiom and look like financial statements: generous row
  height, 1px hairline row separators, right-aligned numerics with uniform precision,
  no zebra striping, sort indicated by a thin chevron. Micro-bars/sparklines sit inside
  cells at text height.

### Marks & chart anatomy (encoded as shared-component behavior, not per-chart taste)

- Thin marks: bars with 4px rounded data-ends anchored to the baseline, 2px line
  weight, ≥8px hover targets; a **2px surface gap between stacked segments and
  adjacent bars** (this is what keeps dense stacked bars readable at our skew).
- Grid and axes are recessive (lightest slate, no axis lines where a gridline
  suffices); no chart borders; titles are the construct's named question in sentence
  case.
- Legends always present for ≥2 series; ≤4 series also direct-labeled at line ends;
  values appear on hover (crosshair + tooltip on time series, per-mark tooltip on
  bars/cells/dots), never printed on every mark.
- **One axis, always.** Two measures of different scale are two charts or small
  multiples — never a dual-axis chart.
- **Hatching is the texture system**: one 45° hatch SVG def, used for `undetermined`
  (grey hatch), demo traffic (accent hatch), and small-n heatmap cells (dotted) — so
  uncertainty states survive grayscale printing and CVD, and are never color-alone.
- Empty/ghost states are quiet: ghost cards and empty windows render in the grey ramp
  with a single-sentence explanation — no illustrations, no emoji.

### Technical enforcement

- All of the above lives in **theme tokens + the shared components** (§5): palette
  tokens in the Tailwind theme, mark specs inside the chart wrappers, hatch defs
  mounted once. Page components cannot deviate because they never touch raw colors or
  chart primitives — a construct that needs a color takes a semantic token
  (`series.client[2]`, `status.failure`, `chip.model`).
- Light mode only for v1 (an internal analyst tool; dark mode is a later theme-token
  pass, not a redesign — the validator run repeats against the dark surface then).
- A0 exit includes the validated palette report checked in next to the theme tokens.

## 7. Testing — deliberately minimal (smoke only)

The frontend is **not** a testing focus. UI correctness is validated by humans looking
at it; the test suite exists solely as a tripwire that we didn't totally break the app.
Scope, in full:

- **Render smoke tests**: every route in the sitemap mounts against the fixture pack
  without throwing, including `/session/:id` on the worst fixture session.
- **Navigation smoke tests**: from the findings page, each card/crossover/drill-down
  link resolves to a route that renders; the URL codec round-trips (URL → state → URL)
  for a couple of representative filter/window states.
- That's it. No component-behavior tests, no data-layer assertion suites, no snapshot
  tests, no visual regression. If a smoke test needs elaborate setup, the harness is
  wrong — everything runs against the checked-in fixture pack.
- One exception retained because it protects the *cross-track* boundary, not the UI:
  **contract conformance** — fixture files zod-parse against `contracts/` schemas.
  (This is really a contracts test that happens to live near the app.)

Anything beyond this scope is explicitly out; correctness of queries, captions, and
semantics is verified by eye during development and by the ETL-side tests where the
data itself is concerned.

## 9. Deliberately not built

Per ui.md's cut list, plus: no SSR/framework meta-layer (static SPA is the deployment
contract), no state management library, no component library (the honesty affordances
are the design system), no i18n, no visual regression infra.
